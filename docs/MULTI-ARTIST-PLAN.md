# 多艺术家署名修正与三端适配方案

## 状态与范围

- 状态：首轮代码已实施并通过可运行检查，待真实曲库与 Android / Windows 验收。本文保留完整设计目标，实际范围及偏差见下节。
- 涉及项目：032 Music Server、Android MusicBridge、Rust 032player。
- 修改范围包含 MusicAutoTagger，用于修复多人标签写入根因。未操作真实曲库。
- 不修改音频文件，不全库按逗号拆名，不重构播放上报，不增加其他服务端抽象。
- 示例：`Mori Calliope, 常闇トワ` 应关联两位独立艺术家，而不是建立一个临时组合。尚未取得该曲目的实际标签或 API 返回，不能断言该样本的数据在哪一层出错。

## 本轮实际交付与设计偏差

1. MusicAutoTagger 旧实现确实只写拼接 `ARTIST`，没有逐人的 `ARTISTS`。现已贯穿 MusicBrainz 解析、元数据复制及容器写入，新增结构化曲目/专辑姓名列表。
2. 服务端优先读结构化标签，并支持旧刮削器的“英文逗号展示名 + 多个有效 MBID”数量严格匹配恢复；没有增加在线 MusicBrainz 查询。完整扫描可修复符合条件的现有文件，不要求重写音频。
3. 实际迁移 067-069：`track_primary_artist_state` 使用 JSON 保存当前人工人员，`track_primary_artist_base` 保存底层关系，`track_primary_artist_operations` 保存版本历史；另加已验证的文件/艺术家/MBID 对应关系。没有照搬下文建议的全部表名。
4. 管理页本轮只做单曲预览、确认、恢复默认、最近操作撤销，选择已有艺术家。批次修正和艺术家创建暂缓，避免在有完整标签的曲库里引入多余批量改库风险。
5. Rust 文字署名统一使用 `姓名 | 姓名` 独立链接，覆盖主要曲目、专辑、首页和正在播放入口；只有右键等单一艺人入口保留多人选择器。专辑归属与曲目合作独立：个人专辑含合唱仍归本人发行，客串方归参与作品；非合辑的共同专辑署名归合作发行，VA 合辑中的合唱归参与作品，双方仍能查询曲目。
6. 两端收到新曲目数据后仅刷新队列艺人元数据，不重建播放会话。Android 下载数据库升为 v19，保留离线身份引用。
7. 没有新增同步协议；Android 完整刷新发现旧曲目的修改，Rust 重新加载相关曲目数据。纯离线不自动获知服务端变化。
8. 合并回退保护采用保守的全局人工版本指纹：之后任何人工署名编辑都会阻止回退，不仅限受影响曲目；该限制已写入服务端使用文档。
9. 真实样本尚未提供，验收不能标完成。SQLite/Robolectric 原生库不支持当前 ARM Linux，Android 数据库相关测试需 x86_64 CI 或真机；APK 编译和所选纯 JVM 测试已通过。

## 1. 已确认的代码事实

### 1.1 服务端

参考路径相对 [032music-server](https://github.com/lux032/032music-server) 仓库根目录：

| 路径 | 事实 |
|---|---|
| `internal/metadata/artist_credits.go` | `ArtistNames` 优先读 `ARTISTS`，再读 `ARTIST`；不按英文逗号、`&` 猜测拆分 |
| `internal/metadata/reader.go` | `SplitPeople` 支持分号、带空格的斜杠、顿号；专辑艺人有独立读取路径 |
| `internal/storage/library.go` | 导入会重建 `track_artists`；直接修改关系会被完整重扫覆盖 |
| `internal/storage/enrichment.go` | `track_artist_sources` 物化是追加式；`manual` 排序靠前不等于替换旧关系 |
| `internal/storage/track_extras.go` | 曲目展示文字、结构化引用从关系表生成；修正生效关系可覆盖现有读取 API |
| `internal/storage/sync.go` | 同步是按 ID 游标分页，不是按修改时间增量；`SyncTrack` 没有独立的署名版本 |
| `internal/storage/artist_api.go` | 艺人曲目查询包含曲目署名与专辑署名两种关系，不能因曲目修正擅自改变此行为 |
| `internal/storage/missing.go` | 有孤立艺术家清理，必须适配新增的底层引用和审计保留策略 |

### 1.2 Android

参考路径相对 [MusicBridge](https://github.com/lux032/MusicBridge) 的 `app/src/main/java/com/lux032/musicbridge`：

- `music/MusicModels.kt`：曲目、专辑已有 `List<ArtistRef>`，两类署名分开。
- `music/Music032Json.kt`：解析 `artists` 数组，不必重新发明多人模型。
- `state/AppStateLibraryCoordinator.kt`：单人直达，多人设置 `artistChoices`；无引用时按名字查找。
- `storage/AlbumLocalStore.kt`：有艺术家关联表和序列化引用。整库、专辑更新已存在删除旧关联再写入的路径，需要逐入口测试而非认定全部有缺陷。
- `storage/PlaybackSessionStore.kt`：队列会话已保存引用；旧快照仍可能需要按曲目身份刷新。

### 1.3 Rust

- `crates/api/src/types.rs`：已保留曲目 `artists` / `album_artists` 和专辑 `artists`。
- `crates/core/src/browse.rs`：`track_item`、`album_item` 等视图只保留一个 `artist_id`。
- `crates/core/src/controller.rs`：`NowPlaying` 同样简化为一个 ID。
- `crates/app/ui/views.slint` 等：整串名字共用一个链接。

## 2. 数据契约

1. `artists` 是有序的权威身份引用，按规范艺术家 ID 去重；不按名字去重不同身份。
2. `artist` 是展示文字，不能作为唯一身份或反向写入关系的依据。
3. 曲目演唱者、专辑署名者、幕后角色互相独立。第一阶段仅修正曲目的 `primary` 署名。
4. 真正的组合或乐队保留独立实体；疑似合作署名检测只用于提示，不作为自动修改依据。
5. 继续使用现有读取 API 字段，不提升 `apiRevision`，不要求旧客户端认识新字段。
6. 曲目自身没有署名时维持现有专辑艺人回退。第一阶段人工覆盖必须至少有一个人，不引入“故意置空”的第三种语义。
7. 修正不更换曲目 ID，不改歌单、曲目收藏、播放记录、音频路径和媒体 URL。

## 3. 服务端：持久化覆盖

### 3.1 为什么不能只写 `track_artists`

扫描会删除再重建它，外部补全又可能追加关系。必须让它成为统一生成的生效结果，并在所有 `primary` 写入路径最后应用覆盖。

也不能仅在 API 返回时替换数组：艺人曲目查询、统计、收藏筛选和同步查询仍会读取旧关系。

### 3.2 建议存储

具体迁移编号由服务端实施时按当前版本选择，以下是建议表名，不是已存在的表：

| 表 | 用途 |
|---|---|
| `track_primary_artist_base` | 保存未应用本功能覆盖时的底层有序署名，供恢复标签/底层结果使用 |
| `track_primary_artist_overrides` | 每曲目一条覆盖头，保存持久递增的 `revision`、启用状态和更新时间 |
| `track_primary_artist_override_items` | 当前人工覆盖的有序艺术家引用 |
| `track_primary_artist_operations` | 不可变操作记录，含批次 ID、前后覆盖状态、前后生效署名快照、时间及备注 |

约束：

- 底层、覆盖项按 `(track_id, artist_id)` 唯一，`position` 表示确定顺序。
- 覆盖关闭仍保留覆盖头与版本，避免删除后重新创建导致版本回退。
- 迁移只从现有 `primary` 关系初始化底层表，不猜测拆分，不改现有归属。
- 艺术家 ID 必须存在并解析合并后的规范身份；规范化后重复的目标拒绝提交并提示。
- 操作快照保存 ID 和当时显示名；不能通过级联删除静默丢失审计记录。
- 孤立清理需保护仍被底层、当前覆盖或可撤销历史引用的艺术家。仅增加限制删除外键会让现有清理失败，必须同步改清理查询。

### 3.3 单一写入流程

```text
扫描 / 补全产生底层 primary 关系
  -> 更新底层快照
  -> 解析有效覆盖
  -> 替换 track_artists 中的 primary 结果
  -> 更新受影响实体时间戳及必要缓存
  -> 同一事务提交
```

- 覆盖启用：生效结果只能是覆盖项，不与标签、远程来源取并集。
- 覆盖关闭：生效结果为最新底层快照，不是第一次修正前的过期结果。
- 完整重扫：更新底层，但覆盖保持不变；恢复默认后应看到最新标签。
- 后台补全：更新底层及来源记录，不得向启用覆盖的生效结果追加 `primary`。
- 幕后角色保持原实现，不因覆盖被删掉。
- 删除曲目时清理当前状态；历史的保留/归档应遵循服务端现有删除约定，不阻断正常曲库清理。

实施前必须枚举全部 `primary` 写入路径，包括导入、来源恢复、补全、艺术家合并与合并回退。新增覆盖与底层表不能成为绕过现有合并机制的第二套身份系统。

艺术家合并必须解析或迁移相关引用、去重并重新物化。合并回退不得覆盖之后发生的人工纠正：有后续编辑冲突时拒绝回退，不能猜测恢复。两类操作都需要独立回归用例。

### 3.4 修改、恢复默认与撤销

区分三种操作：

- **设置覆盖**：写入指定曲目的有序人员列表。
- **恢复默认**：关闭覆盖，使用最新底层结果。
- **撤销本次操作**：恢复该操作前的覆盖配置，再根据当前底层计算结果；若底层标签已变化，预览明确展示差异，不声称恢复为完全相同的旧文本。

每次成功修改递增版本，审计、物化、时间戳更新同事务完成。重复提交使用操作令牌防重，不应多写一份历史。

并发保护：提交携带预览时的覆盖版本和底层/生效关系指纹。期间有人修正、重扫改变底层或艺术家合并时，返回冲突并要求重新预览。不能只检查覆盖版本。

第一阶段只支持撤销当前最新且未冲突的操作。历史任意版本恢复、多级跨操作回滚不做。

## 4. 管理端：历史修正入口

修正先集中在服务端管理页，不要求 Android、Rust 提供写接口。

### 4.1 最小流程

1. 从曲目详情或疑似合作署名艺术家页进入“修正演唱者”。
2. 显示当前生效人员、底层标签、是否已有覆盖。
3. 搜索并选择已有艺术家，支持调整顺序。没有目标时使用现有艺术家创建能力；若服务端没有该能力，再增加显式创建，不允许静默按文本建人。
4. 明确选择曲目，批量操作必须枚举具体 ID；不是“以后所有这个名字自动拆分”。
5. 预览每首修改前后、涉及专辑、未修改的专辑署名及已有覆盖。
6. 确认后提交，返回操作批次与成功结果，可进入撤销预览。

建议第一阶段批次最多 100 首；超限提示分批。每批全成功或全回滚，任何版本冲突都不部分写入。数量限制以服务端实施时的测试结果复核。

### 4.2 安全边界

- 现有管理员会话与 CSRF 防护；只读 API Token 不获得管理写权限。
- 人名和标签按不可信文本转义，不将来源文本直接拼成 HTML。
- 自动识别只给候选，不预选全库并执行。
- 原合作署名实体不重定向到任意一位个人，不迁移个人身份、图片、简介或艺术家收藏。
- 原实体仍有专辑署名或其他有效角色时，保留显示；没有有效曲库关联但因底层或历史被保留时，不在普通艺人列表冒充活跃艺人。
- 专辑署名修正作为后续独立能力；本期只提示，不隐式联动。

## 5. Android：复用多人能力，补齐刷新

### 5.1 交互

保持当前“单人直达，多人弹选择器”，不为本次适配重做播放页。参与者顺序来自数组，不能重新按名字排序；选择器使用标准可访问点击行。

没有结构化引用时只做显示与兼容查找，不把猜测持久化为曲库归属。正常多人引用优先，不能再次对名字按逗号拆分。

### 5.2 同步与缓存

- 按服务器身份 + 曲目 ID 更新，替换 `artist_refs` 和旧链接；整库、单专辑、歌单、收藏、单曲刷新分别验证。
- 明确同步不是变更流。第一阶段通过现有完整曲库刷新重新拉取旧 ID，不依赖游标继续向后读取发现修改。
- 同一轮刷新完成后发布更新，防止旧异步响应覆盖新关系；失败保留上一份完整结果。
- 刷新艺术家列表与曲目关系，确保两个个人页都能查到歌曲；不全局替换展示文本。
- 刷新当前队列、收藏和下载记录可用的新元数据，不改变队列位置、上下文、播放会话和已下载音频。
- 离线时继续用最后已知数据，不承诺离线自动获知服务端修正。
- 检查曲目无自有引用时能否取得专辑引用；缺失时降级展示，不错误归到第一个匹配名。

先用现有完整刷新闭环，不新增推送、增量同步协议或每条进度事件网络查询。若现有入口不能刷新所需曲目，再在实施中补最小刷新入口。

## 6. Rust：把数组传到展示层

- `core::browse` 视图增加有序艺人引用，`NowPlaying` 保留相同结构，不再以第一位 ID 代表整串名字。
- 曲目行、版本列表、专辑卡片、详情头、首页、播放条、右栏、全屏播放器逐入口审计。
- 有独立姓名的文字链接分别跳转；单一“转到艺人”菜单入口多人时列出选择项，绝不静默选择第一位。
- 空间不够时整体省略或提供多人菜单，不用索引裁切字符串推算可点击范围；保留现有视觉风格。
- 艺人引用缺失时显示文字，只有经确认的 ID 才能跳转；专辑回退保持一致。
- 队列旧快照按需补取新元数据；刷新不得重新开始播放、增加上报次数或丢失推荐上下文。
- UI 假数据包含双人、多人、长名字、无 ID 与真实组合；截图验证宽窄窗口及中文/日文。

## 7. 顺序与交付边界

### S0：样本与契约

- 获取一首有问题曲目的 ID、`GET /tracks/{id}` 返回及原标签；凭据脱敏，不保存媒体 Token。
- 用合成测试样本覆盖没有真实曲库访问的情况；真实样本验证列为待办，不阻塞单元测试编写。
- 确认目标人员在曲库中的现有 ID，排除只是客户端整串高亮。

### S1：服务端存储

先实现迁移、统一物化、修正/恢复默认/撤销、并发及合并兼容测试，再加管理页面。读取 API 保持兼容。

### S2：Android

先证明现有解析和选择器正确，再补同步、缓存与离线元数据更新缺口。尽量不增加数据模型或数据库迁移。

### S3：Rust

引用贯穿视图、多人跳转、队列刷新和 UI 快照。可先用合成 API 测试，不要求服务端先部署才能开发。

### S4：联合验收

部署服务端并修正样本，Android 完整刷新，Rust 重新加载；最后一次性做真机与 Windows 验收。

## 8. 验收矩阵

| 用例 | 预期 |
|---|---|
| 双人 / 三人、已有 ARTISTS / 多值 ARTIST | 人员及顺序正确，每位均可查询曲目 |
| 带逗号的个人名、含 & 的真实组合 | 不自动拆分 |
| 同曲不同专辑署名 | 仅修改所选曲目的 primary，不改变专辑与幕后 |
| 重扫、后台补全、来源恢复 | 覆盖不回退、不被追加污染 |
| 覆盖期间标签变化，恢复默认 | 使用最新底层署名 |
| 批次中有无效 ID、版本冲突 | 全批回滚，无部分修正 |
| 重复提交、重启后撤销 | 不重复应用；版本及历史持久 |
| 合并目标人员、合并回退、随后人工编辑 | 规范 ID 一致；冲突不覆盖后续编辑 |
| 孤立清理、删除曲目 | 不破坏可恢复状态，也不阻塞正常扫描清理 |
| 普通查询、browse、sync、收藏、搜索、作品/推荐曲目 | 同一曲目返回相同生效人员与展示文字 |
| Android 完整刷新、单专辑刷新、队列恢复、离线 | 无残留旧关联；离线保留最后已知数据 |
| Rust 所有艺人入口 | 分别跳转或明确选择，不整串跳第一位 |
| 播放中刷新两端元数据 | 队列和播放上报会话不重建，音频不重下载 |
| 修正与撤销前后 | 曲目 ID、歌单顺序、曲目收藏和播放历史不变 |

## 9. 暂不做

- 全库自动按标点拆分、AI 无确认修复、修改音频标签。
- 自动把合作署名的收藏或外部身份复制给个人。
- 专辑艺人、所有幕后角色的通用覆盖框架。
- 客户端署名编辑器、实时推送、全新同步协议。
- 任意历史版本回滚、无上限批量改库。
