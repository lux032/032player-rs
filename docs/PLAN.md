# 规划

整理自 2026-10-28 的路线评估，并按后来的实现更新了状态。

当前版本 0.2.15 可以日常听歌。下面的里程碑是当时的切分：M0 到 M3 的代码已经落地，M4 的打磨还在进行。剩余缺口见文末和 `TASKS.md`。

## 背景

Electron 版 032musicplayer 的规模（2026-10）：

| 部分 | 行数 | 说明 |
|------|------|------|
| `src/renderer`（React UI） | 约 14.4 万 | 重写成本主要在这里 |
| `src/main`（Electron 主进程） | 约 9 千 | mpv、MPRIS、托盘、更新、远程控制 |
| `src/shared` | 约 1.8 万 | 类型、normalize、主题 |
| 032 专属 API + 上报 | 约 3.1 千 | 纯逻辑，容易移植 |

技术栈：Electron 43、React 19、Mantine 9、react-query、zustand、motion、OverlayScrollbars、
react-window，播放走 `node-mpv`（mpv 子进程 + IPC socket）。

要点：**音频本来就是原生 mpv**，bit-perfect / 独占模式不依赖 JS。Rust 重写改善的是
UI 流畅度和资源占用（内存、启动、包体），不是音质。

## 两类"性能不好"

1. 内存高、启动慢、包体大：Electron 自带 Chromium 的固有成本。
2. 滚动卡、切页慢、播放时掉帧：React 层问题（进度 tick 引起大范围重渲染、
   `player.store.ts` 订阅粒度、动画、滚动条库、react-query 持久化缓存）。

## 路线对比

| 路线 | 工作量 | 解决 1 | 解决 2 | 备注 |
|------|--------|--------|--------|------|
| 0. 原地优化 Electron 版 | 1-3 周 | 否 | 大部分 | 投入产出比最高，可在 Electron 仓库里独立进行 |
| 1. Tauri 2 + 复用 React | 1.5-3 月 | 是 | 否 | 只重写主进程；Linux WebKitGTK 可能更慢 |
| 2. 全原生 Rust | 6-12 人月对齐 | 是 | 是 | 本仓库选的路线 |

**决定：本仓库做路线 2。** Electron 版的优化可另行在 Electron 仓库进行，两者不冲突。
路线 2 按里程碑推进；日常听歌所需的部分已经可用，对齐和打磨还没结束。

## 已定决策

| # | 决策 | 状态 |
|---|------|------|
| D1 | 独立仓库，与 Electron 版分开 | 已定 |

| D3 | 播放用 libmpv（`libmpv2` crate），进程内调用，不走 socket | 已定 |
| D4 | 只支持 032 Music Server；不做多服务端抽象 | 已定 |
| D5 | 主力平台 Windows，其次 Linux，macOS 尽力而为 | 已定 |

UI 框架备选（D2 在 M0 不过关时再选；M0 后仍用 Slint，备选保留作记录）：

| 框架 | 优点 | 缺点 |
|------|------|------|
| Slint | 声明式 `.slint`，内置虚拟化 ListView，Windows / IME 成熟，内存低 | 复杂自定义布局（主页轮换、逐字歌词）要多花功夫 |
| gpui + gpui-component | 性能最强，组件库自带表格 / 虚拟列表 / 主题 | API 不稳定，文档少 |
| iced | Elm 架构，社区大 | 无内置虚拟列表 |

## 当前不做

以下 Electron 版功能默认不在当前范围内（M4 打磨之后再考虑）：

- 远程控制（内置 HTTP 服务 + 远程 SPA）
- Discord Rich Presence
- 可视化
- 自定义主题（导入 CSS 的那套无法沿用，要重新设计）
- DLNA 投放（Sonos 投放已做，2026-11-08，照搬 MusicBridge；普通 DLNA 仍不做）
- 标签编辑器（本地 taglib）
- 其余语言（界面保持简体中文）

### M4 后续排序（2026-11-06）

日常以深色为主。按"日常听歌会碰到的缺口优先"排。1 到 6 已按这个顺序做完；第 5 项只做到提示，不自动安装。

1. 淡入淡出：只做播放 / 暂停时 300 ms 渐变（Electron mpv 引擎 `audioFadeOnStatusChange`，默认开），设置页开关；
   切歌不淡化，不做交叉淡化（与无缝 / bit-perfect 冲突，Electron 的 mpv 引擎也没有）。渐变走独立增益，不改保存的音量。
2. 全屏播放器：窗口内覆盖层（盖住侧栏和内容区，保留播放条），原图封面 + 元数据 / 音质，页签"歌词 / 接下来播放 / 相关歌曲"，
   背景复用 `core::backdrop`；不做可视化和配置弹窗（固定 Electron 默认值）。入口：播放条封面、侧栏底部封面、歌词按钮（直接到歌词页签），Esc 收起。
3. P0 零碎项：设置页右栏开关、曲目"查看信息"（与全屏播放器元数据共用字段）、艺人页分组播放按钮、"收藏的歌曲"。
4. 032 Light / Dark + 跟随系统，默认深色（评估：442 处颜色已走 `Theme`，写死的 24 处都是封面上的遮罩，成本约一批），优先级最低。
5. 自动更新最简版：启动时查 GitHub Releases，有新版提示并给链接，不自动安装。这项可能拿掉。

6. Sonos 投放（2026-11-08，参考 MusicBridge）：客户端直接控制音箱（SSDP + UPnP SOAP），不走服务端 `/api/v1/cast`
   （那条路服务端不上报播放，且要求服务端和音箱同网段并额外配置）。只做 032 队列模式，入口在播放条独占旁边，见 `FEATURES.md`「Sonos 投放」。

不做：均衡器 / 压缩器、ReplayGain（服务端不给增益）、i18n（只保留简体中文）、静音按钮、全局快捷键、最小化到托盘、代码签名。
验证清单不逐条作为发布门槛。使用中发现的问题记到 `TASKS.md`。

## 多艺术家署名修正（三端适配）

服务端、Android MusicBridge、Rust 桌面端用同一套方案。详细设计见
[`MULTI-ARTIST-PLAN.md`](MULTI-ARTIST-PLAN.md)，任务见 `TASKS.md` 同名小节。

- 服务端权威维护关系，结构化标签优先，不全库按逗号猜测拆分；新增可持久、可撤销的曲目演唱者覆盖。
- 曲目艺人、专辑艺人与幕后角色独立，本期不隐式修改专辑署名。
- Android 复用现有多人引用与选择器，重点验证同步、本地关联、离线及队列元数据刷新。
- Rust 补齐多人引用的视图传递与分别跳转，不能把整串名字链接到第一位。
- 现有读取 API 字段够用，不新增同步协议。MusicAutoTagger 另补结构化标签写入。
- 首轮代码和可运行检查完成，实际范围及设计偏差见方案文档；真实样本、Android 数据库测试和真机验收未完成，见 `MULTI-ARTIST-ACCEPTANCE.md`。

## 风险

| 风险 | 应对 |
|------|------|
| 中日文字体回退、输入法 | M0 必测；后来内嵌 Noto 字体 |
| 逐字卡拉 OK 歌词渲染 | 032 歌词只有逐行时间，逐字不做 |
| 大量封面图的解码和缓存 | 后台线程解码 + 磁盘缓存 + 按尺寸请求（服务端支持 `size`，注意 `size=0` 会被拒） |
| 主页等复杂布局 | M3 再做，必要时简化 |
| libmpv 在 Windows 的分发 | 随包带 `libmpv-2.dll`，构建脚本下载 |
| 工作量超出当时的估计 | 范围按里程碑切分；未做项留在清单里，不为其他服务端加抽象 |
